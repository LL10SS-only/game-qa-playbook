## 统一的四段式

这 5 张图不是各写各的，用的同一个骨架：

```
1. 文档和干系人员   ← 需求文档、UX 稿、策划/程序/UX 对接人
2. 功能逐项        ← 系统本身的每个功能点
3. 交叉与异常      ← 与其他系统的交叉、断线、热更、红点
4. 收尾            ← 标色释义、遗留问题、待补充
```

第 1 段是最容易被省掉的，也是我坚持保留的。理由很实际：**一个系统测到三个月后，最先忘掉的是"这个需求当初找谁确认"**。写在图里，接手的人不用翻聊天记录。

第 4 段的"标色释义"是一套颜色约定：已执行、阻塞、待补充、不适用。脑图没有字段，颜色就是状态字段。

## 各系统的一级模块

**天赋树**（15 项）：入口检查、主天赋树正确性、资源点获取、解锁检查、点亮/升级检查、重置检查、技能管理页、被动技能、天赋介绍、默认天赋、效果检查、红点逻辑、热更检查——外加策划案链接与标色释义。

这份的价值在**"重置"和"热更"两个模块**。绝大多数人写天赋系统只会写"能不能点亮、能不能升级"，但天赋重置涉及**资源返还与已消耗资源的追溯**，热更则涉及**玩家已点天赋在配置变更后的合法性**——这两个是天赋系统真正的坑。

**交互物通用机制**（9 项）：散件、交互类型、交互流程、交互机制优化、可交互物优化、3P 检查、断线重连、策划案。

注意它有独立的"断线重连"模块——通用机制类系统必须单独验断线，因为它是被所有玩法复用的，一个断线问题会扩散到全部交互。

**道具系统**（13 项）：获取途径、道具类型、品质、形状大小、价值、效果、消耗品与可堆叠物、道具 tips……

**商人系统**（12 项）：布局检查、商品浏览、排序规则、商品卡片、道具 tips、上架/下架、购买、购买界面……

商人系统和道具系统的重叠处（道具 tips、品质、价值）是最容易出问题的地方：**同一件道具在两套系统里的展示规则如果不一致，玩家会看到两个价格或两种描述**。所以这两张图我都单独留了 tips 模块，专测"同一数据在两个入口的呈现是否一致"。

## 局限

- **这是测试点，不是用例。** 一个节点展开成几条用例取决于版本阶段：冒烟阶段可能 1 条，全量阶段可能 5 条。所以节点数不能直接当用例数报。
- **交叉模块普遍偏薄。** 每个系统都留了"与其他系统交叉"，但实际展开的深度不一致，交互物那张做得最细，道具那张最粗。这是当时的真实状态，不是设计如此。
- **没有版本维度。** 脑图只记录"要测什么"，不记录"哪个版本测过"。版本追溯在缺陷系统和测试报告里，不在脑图里——脑图不适合承载时间信息。
