# 03 系统模块测试点

5 张系统级脑图，合计 3881 节点。这些不是用例清单，是**测试点框架**——每个节点代表一个"要测的地方"，展开成多少条用例由模块复杂度和版本阶段决定。

| 系统 | 节点数 | 一级模块数 |
|---|---|---|
| 玩法 · 交互物通用机制 | 1195 | 10 |
| 战斗 · 天赋树 | 1162 | 21 |
| 道具系统（非装备） | 904 | 8 |
| 交易 · 商人系统 | 425 | 9 |
| 大厅 · 系统选单界面 | 195 | 4 |

## 统一的四段式

这 5 张图不是各写各的，用的是同一个骨架：

```
1. 文档和干系人员   ← 策划案、UX 稿、策划/程序/UX 对接人
2. 功能逐项        ← 系统本身的每个功能点
3. 交叉与异常      ← 与其他系统的交叉、断线、热更、红点
4. 收尾            ← 标色释义、专项、待补充
```

第 1 段最容易被省掉，也是我坚持保留的。理由很实际：**一个系统测到三个月后，最先忘掉的是"这个需求当初找谁确认"**。写在图里，接手的人不用翻聊天记录。

第 4 段的"标色释义"是一套颜色约定：已执行、阻塞、待补充、不适用。脑图没有字段，颜色就是状态字段。

## 各系统的一级模块

**天赋树（21 项，最完整的一张）**
策划案、标色释义、入口检查、主天赋树正确性、天赋资源点获取、天赋解锁检查、天赋点亮/升级检查、天赋重置检查、技能管理页、被动技能检查、天赋介绍检查、默认天赋检查、天赋效果检查、红点逻辑检查、天赋热更检查、按键提示与操作触发检查、交叉：英雄切换界面、天赋类型 UI 检查、音效检查、界面检查、专项。

这张的价值集中在三个别人不太写的地方：

- **天赋重置**：涉及资源返还与已消耗资源的追溯，是天赋系统里唯一会动玩家资产的操作
- **天赋热更**：配置变更后，玩家已点天赋是否仍然合法、点数是否对得上
- **交叉：英雄切换界面**：天赋挂在英雄上，切英雄时天赋页的状态残留是典型问题

**交互物通用机制（10 项）**
策划案、需求链接、散件、交互类型、交互流程、交互机制优化、可交互物优化（两类）、3P 检查、断线重连。

它有独立的"断线重连"模块——这是我认为通用机制类系统必须做的：**它被所有玩法复用，一个断线问题会按玩法数量扩散**。

**道具系统（8 项）**
获取途径、道具类型、品质、形状大小、价值、效果、消耗品与可堆叠物、道具 tips。

**商人系统（9 项）**
文档和干系人员、布局检查、商品浏览、商品排序规则、商品卡片、商品的道具 tips、上架/下架、购买、商品购买界面。

**系统选单界面（4 项）**
文档和干系人员、局外、局内、更新内容。这张最薄，因为它是一个纯 UI 聚合层，功能都在各子系统里。

## 一处容易漏的交叉

商人和道具两张图都有"道具 tips"模块，这不是重复。

**同一件道具在背包里和在商店里，展示规则可能不一样**（价格要不要显示、能不能对比、品质颜色是否一致）。如果两套系统各自维护一份展示逻辑，玩家就会看到同一个道具两个价格或两种描述。

所以这两张图我都单独留了 tips 模块，专测"同一份数据在两个入口的呈现是否一致"。这类问题不进任何一个系统的单测，只在交叉时暴露。

## 局限

- **这是测试点，不是用例。** 一个节点展开成几条用例取决于阶段：冒烟 1 条，全量可能 5 条。所以 3881 这个数不能当用例数报。
- **交叉模块的深度不一致。** 每个系统都留了"交叉"位置，但实际展开程度差别很大——交互物做得最细，道具那张最粗。这是当时的真实状态，不是设计如此。
- **没有版本维度。** 脑图只记"要测什么"，不记"哪个版本测过"。版本追溯在缺陷系统和测试报告里，脑图不适合承载时间信息。
