# 01 场景模块用例

一个大型 PVP 地图场景模块的全量用例库，加上一套场景检查项框架。这两份是配套的：框架负责"想到哪些面"，用例负责"每面测到什么程度"。

## 规模

| 项 | 数量 |
|---|---|
| 用例条数 | 854 |
| 脑图节点 | 6013 |
| 优先级分布 | P0 47 / P1 502 / P2 305 |
| 框架检查项 | 15 类（784 节点） |
| 单条用例字段 | 6 个（用例名、前置条件、操作步骤、预期结果、优先级、适用端与模式） |

6013 ÷ 7 ≈ 859，和 854 对得上——因为每条用例固定占 7 个节点（1 个用例名 + 6 个字段），这个结构一致性能保证脑图可以直接转成表格，不用人工二次整理。

## 用例长什么样

直接从脑图里摘的 4 条，原文未改：

| 用例名 | 前置条件 | 操作步骤 | 预期结果 | 优先级 |
|---|---|---|---|---|
| 空气墙碰撞检查 | 已进入游戏场景 | 检查空气墙是否透明不可见 | 空气墙透明不可见，不影响正常游玩视野 | P0 |
| 空气墙碰撞检查 | 处于地图边界附近 | 尝试进入 / 跑出非正常游玩区域、地图边缘 | 空气墙可正常挡住玩家，玩家无法进入 / 跑出非正常区域 | P0 |
| 空气墙碰撞检查 | 已驾驶载具 | 驾驶载具尝试穿过空气墙 | 无法穿过，空气墙可阻挡载具通行 | P0 |
| 空气墙碰撞检查 | 正常进入对局 | 检查空气墙是否透明不可见 | 是透明不可见 | P1 |

四条同名，靠前置条件区分——**这是这类模块用例的关键组织方式**：同一个检查点在"步行 / 载具 / 边界 / 正常"四种状态下表现不同，写成四条比写一条加备注可靠，因为执行的人不会漏看备注。

## 一个设计取舍

预期结果写"是透明不可见"和写"空气墙透明不可见，不影响正常游玩视野"是两种质量。前者只能判断有没有，后者能判断"透了但挡了视野"这种真实存在的问题。

但全库都按后者写会导致**执行时判据发散**——执行的人会开始按自己的理解解读"不影响视野"。所以实际做法是：**P0 写全，P1/P2 写短**。P0 是发布门禁，判据必须闭环；P1/P2 追求覆盖率，判据留一点弹性反而跑得快。

## 局限

这套用例覆盖不了三件事，写在这里是因为迟早会被问到：

1. **多人并发下的状态竞争**：两条用例分别测"玩家 A 触发"和"玩家 B 触发"都是通过的，但同时触发时的结果没人测。这类问题要到专项阶段用多端同时操作才能发现。
2. **数值平衡**：用例只能验证"伤害按配置表计算"，验证不了"这个数值合不合理"。后者是策划的事，测试能给的是数据，不是判断。
3. **长时间运行的累积问题**：连续跑图两小时后的内存增长与碰撞体错位，属于稳定性专项，不在功能用例范围内。

这三类如果没人负责，正确做法是在测试报告里明确标"未覆盖"并写清由谁补——**含糊过去，最后是玩家替你发现问题**。
