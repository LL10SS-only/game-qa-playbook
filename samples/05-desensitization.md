# 脱敏口径

作品集要能被看见，就不能带着项目信息出门。这一篇写清楚我在公开前做了什么、按什么标准判断，以及哪些东西我决定不公开。

## 三类处理，粒度不同

| 类型 | 处理方式 | 为什么这么处理 |
|---|---|---|
| 可识别的文本 | **整段替换为 `***`**，不留前后缀 | 只删关键词会留下"XX系统"这种半截，反而更好猜 |
| 截图 | **按原尺寸重绘为灰块** | 打码/模糊处理在视觉上仍保留布局、图标、配色，能反推出界面。重绘是把像素清空 |
| 结构 | **零改动** | 层级、编号、行列、排版都不动。改结构就没法证明我当时的组织能力 |

## 具体扫了哪些地方

一开始只删了正文，漏掉一半。补完之后的清单：

**脑图类**
- 节点标题（第一遍只处理了这个）
- `attributedTitle` 富文本里的同款文字
- `notes` 备注、`label` 标签
- `href` 超链接属性——标题改成了 `***`，链接还挂在上面等于白改
- `metadata.json` 的作者字段
- `tdoc-content.json`——线上预览用的镜像文件，内容和 `content.json` 同源，只改前者不改后者等于没改

**表格类**
- 单元格文本（共享字符串）
- 「数据验证」下拉列表的 `formula1`——里面存着负责人姓名和版本代号，这个位置几乎没人会想到
- 工作表 `codeName`（内部命名，和显示名不同）
- `_rels` 里的外部超链接目标——21 处指向内部系统，链接关系不删的话点一下就能跳回原文档

**文件名**
- 版本代号、里程碑代号、项目前缀。文件名是最容易漏的：内容清干净了，附件名还叫 `XX-SP21（M2）`

## 第二轮：漏掉的那一类

第一轮做完是 413 处，按载体重了一遍，自己觉得干净了。后来又扫一次，发现漏了一大类：**角色名**。

它不是漏在某个隐蔽的 XML 位置，就明明白白躺在单元格的正文里：

- **组合名**：英雄名 + 武器后缀，像 `XX-长矛`、`XX-剑盾`
- **兵种全名**：怪物名字，长得像玩法描述（"流亡士兵""断臂战俘"），读着不像专有名词
- **写在步骤里**：`对敌方XX进行攻击`、`XX 给自己套盾`——夹在操作序列中间，扫十遍也不会觉得扎眼

补了 34 处（英雄 21、怪物 13），用等长映射替换（英雄 A–D、怪物甲–己），行列结构一处没动。改完逐项核对：9 个工作表、1380 行、57 个包内条目，与改前完全一致。

所以最终是 **413 + 34 = 447 处**。

**这一类比 URL 危险得多。** URL 一眼就知道该删；角色名混在句子里，语法上完全通顺，内容审查和肉眼通读都容易滑过去。而且它恰恰是最不该外流的——URL 泄露的是文档地址，角色名泄露的是在研内容本身。

这件事的教训不是"要更仔细"，是**词表本身要分类**：第一轮只想着"公司标识"，第二轮才想到"游戏内容"。这两类该用两张表分别扫。

## 判定标准

一句话：**具备识别价值的公司侧信息一律替换，通用测试语言原样保留。**

替换掉的：员工姓名与账号、内网地址与凭据、内部工具与平台名、需求/缺陷 ID、版本与构建代号、项目与关卡名称、截图画面。

保留的：「设置」「返回大厅」「3v3 模式」「前置条件」「预期结果」这类通用表述——它们不含识别信息，删了反而让文档读不懂。

## 我决定不公开的东西

原始文件（10 份）留在本地。原因不是流程没做完，而是**脱敏能去掉"这是谁的、哪个项目的"，去不掉"这是个什么游戏、怎么设计的"**。后者本身就是项目信息。

所以这个仓库里没有原始文件，只有结构说明。如果你需要看实例，面试时我可以打开讲——**这也是一种测试：能不能把一份不能外传的文档讲清楚，本来就该考。**

## 一点体会

做这件事之前我以为脱敏就是查找替换。做完发现真正的难点是**枚举载体**：同一段文字在脑图里至少有四个副本（标题、富文本、备注、预览镜像），在表格里至少有三个位置（单元格、验证列表、超链接关系）。

**漏掉任何一个，前面的都白做。** 这件事和找 bug 是同一个思路——不是找出问题，是穷举出"问题可能藏在哪"。
