# 缺陷单模板

复制下面这块，按提示填。填不满的字段留空比瞎写强——空着别人知道要问，写错了别人会信。

```markdown
## 标题
[模块] + [在哪] + [做了什么] + [导致什么]

反例：背包有 bug
正例：背包满时从地面拖入同 ID 可堆叠道具，道具消失且未进入背包

---

## 环境
- 客户端版本：
- 设备 / 系统：
- 画质 / 帧率档位：
- 网络：WiFi / 4G / 弱网工具（限速值）
- 账号状态：（等级、背包占用、相关任务进度，必要时截图）

## 复现率
x / y（例如 2/10）。不要写"偶现"，写清试了几次中了几次。

## 复现步骤
1. 从哪个界面开始
2. 具体操作（按键序列，不写"进行操作"）
3. ……
4. 现象出现

## 期望结果
（可观测的描述，不写"应正常"）

## 实际结果
（可观测的描述，附图/录屏）

## 影响判断
- 影响面：多少玩家 / 多少局能遇到
- 阻断性：能否继续游戏
- 可绕过性：有无替代路径，重启是否恢复
- 是否涉及数据不一致：是 / 否

## 定位信息（有则填）
- 抓包 / 请求响应：
- 客户端日志片段（带时间戳）：
- 服务端返回码：
- 数据库核对结果：
- 疑似归属：客户端 / 服务端 / 配置 / 需求待明确

## 附件
- 录屏（含现象出现的确切时间点，例如 00:23）
- 截图
- 日志文件
```

## 几条硬规则

1. **标题里必须有"在哪"**。没有位置的标题，开发第一个问题就是问位置。
2. **复现率必须写成比例**。`2/10` 和 `偶现` 是两种完全不同的信息量。
3. **期望结果和实际结果要能对比**。写"显示错误"没法对比，写"显示 3 个，实际显示 0 个"能对比。
4. **定位信息写"证据"不写"结论"**。写"我觉得是服务端问题"没用，写"请求响应里 itemCount 字段返回 0"有用。
5. **判不清归属就写"待明确"并附证据**，不要硬猜一个方向，会把开发带偏。
