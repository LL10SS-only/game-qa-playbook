# 从需求到用例：场景类玩法的拆解顺序

## 结论

拿到一段需求，先别打开用例模板。按这个顺序想四遍，比直接挑设计方法快得多：

1. **定边界**：哪里能去、哪里不能去，边界上会发生什么
2. **拆状态**：这个东西有几种状态，状态之间怎么迁
3. **找环**：资源和进度是不是闭环，环在哪里可能断
4. **补异常**：断线、掉帧、延迟、队友退出、中途加入

四步走完，用例的骨架就有了。等价类、边界值、状态迁移这些方法是在这四步里**顺手用**的，不是起手式。

一上来就问"这个需求该用等价类还是正交实验"，通常说明还没想清楚要测什么。方法是为已经想清楚的东西服务的。

## 第 0 步：需求里必须先问清的五个问题

需求文档大概率不会写全。下面五个问题缺任何一个，用例都会白写一批：

| 问题 | 缺了会怎样 |
|---|---|
| 谁触发？玩家主动，还是系统定时/被其他玩家触发 | 会把被动触发场景当成主动操作来设计 |
| 在哪触发？限定区域，还是全地图可用 | 会漏掉区域外使用这个最大的异常分支 |
| 失败怎么办？有提示、有回退，还是静默失败 | 会漏掉全部异常态，只测了 happy path |
| 能中断吗？中途取消、切场景、断线后回来 | 会漏掉"半完成态"这一类最难查的问题 |
| 有没有上限？次数、数量、金额、并发人数 | 会漏掉最典型的边界值问题 |

**这五个问题问出来，往往能让策划改一版需求**。这是测试在需求评审阶段唯一的杠杆，比在会上点头有用。

## 一、定边界：先画一条"能/不能"的线

场景类玩法的 bug，绝大多数的本质是**视觉表现和实际判定不一致**。

所以边界不按美术资源画，按**判定体**画：

- 玩家看到能站的地方，碰撞体是否真的能站
- 玩家看到能打穿的缝隙，子弹是否真的能过
- 玩家看到能跳上去的高度，爬升判定是否允许
- 玩家看到被挡住的视线，遮挡判定是否成立

具体做法：拿一张俯视图，把每类判定边界单独描一遍，描的时候只问"这条线两侧的行为是否连续"。

**边界一定是不连续的地方。** 站在线上、贴着线走、以最快速度撞线，这三种操作在边界上的表现可能完全不同，而玩家做出来的动作恰好就是这三种。

> 例子：某张地图的屋顶边缘，站着走会掉下去，但蹲着贴边平移不会触发掉落——因为蹲姿的碰撞盒变矮，下沉检测的射线没打中地面。这不是"穿模"，是两套判定用了不同的碰撞体尺寸。这类问题只有贴着边界做动作才会暴露。

## 二、拆状态：状态迁移表比用例清单好用

先列出对象的所有状态，再列**所有可能的状态对**，然后标出哪些迁移是允许的、哪些应该被拦截。

以角色姿态为例（简化）：

| 当前状态 | 可迁入 | 应被拦截 | 拦截后的期望 |
|---|---|---|---|
| 站立 | 蹲、跑、跳、倒地 | 攀爬（未贴墙时） | 无响应，不播动画 |
| 蹲 | 站、爬行、倒地 | 跑、跳 | 起身再执行，或直接拒绝 |
| 攀爬 | 站立（到顶）、坠落（中断） | 开枪、投掷、拾取 | 输入缓存到落地后，或丢弃 |
| 倒地 | 被救起、死亡 | 移动、攻击 | 仅允许爬行 |

这张表的价值在于**"应被拦截"那一列**。用例通常只写允许的迁移，而线上事故几乎都出在被拦截的迁移没拦住——玩家在攀爬时开枪，动画播了但判定没生效，于是出现了"打中了不掉血"。

做法：

1. 枚举状态 → 得到 N 个状态
2. 列 N×(N-1) 个有序对 → 删掉物理上不可能的
3. 对每个保留的对，问一句"如果玩家在这一刻按了这个键会怎样"

第 3 步会产生大量用例，但不写下来就会漏。**状态机越复杂，漏测的成本越高**，因为玩家总能在你没想过的那一瞬间按下那个键。

## 三、找环：资源和进度闭环

有经济系统的玩法（搜打撤、养成、任务链、通行证），核心风险不在单个功能，而在**环上的断点**。

以搜打撤为例，环是：

```
带入装备 → 局内获取 → 损耗（死亡掉落/消耗）→ 带出结算 → 仓库 → 再带入
```

环上每一段都可能断，且断法不同：

| 断点 | 典型表现 | 怎么测 |
|---|---|---|
| 带入 | 带入的装备在局内不显示/不生效 | 满配带入，逐件核对属性是否生效 |
| 局内获取 | 拾取后背包数量与地面数量不一致 | 同一格位反复拾取丢弃，比对数量 |
| 损耗 | 死亡后该掉的没掉、不该掉的掉了 | 保险箱内外各放物品，分别死亡比对 |
| 带出结算 | 结算界面显示与实际入库不一致 | 结算后立刻查仓库，不走缓存 |
| 仓库 | 仓位满、堆叠上限、跨角色共享 | 卡在上限边界做存入/取出 |

**环的断点几乎都是"两处记录不一致"**，所以这类问题最有效的测法不是点界面，是**同一个事实在两个地方对一遍**：界面显示 vs 实际数据、客户端缓存 vs 服务端记录、结算前 vs 结算后。

## 四、补异常：四类环境异常，不必全测

异常用例是写不完的，按发生的可能性排序，只测前四类：

| 异常 | 为什么优先 | 最小验证点 |
|---|---|---|
| 断线重连 | 移动网络下每天都会发生 | 操作中途断线，重连后状态是否与断线前一致；重连期间的操作有没有被重复执行 |
| 掉帧/卡顿 | 低端机常态 | 在动画中间态卡住，恢复后状态机有没有卡在中间 |
| 延迟/丢包 | 高峰期常态 | 请求已发出但响应丢失，客户端是重试、超时还是回滚 |
| 队友退出/加入 | 多人功能必有 | 房主退出、最后一人退出、中途加入者的状态初始化 |

这四类里最容易被忽略、后果也最重的是**幂等**：断线重连后，玩家刚才那次购买到底是执行了一次还是两次。

## 设计方法什么时候用

| 方法 | 该用的时候 | 别用的时候 |
|---|---|---|
| 等价类 | 输入空间大且有明显分档（数值区间、品质等级） | 输入之间有关联（组合类） |
| 边界值 | 有明确上下限（数量、距离、时间） | 边界本身是浮动的（随装备变化的上限） |
| 场景法 | 有明确的操作流程和目标 | 状态多、流程会交叉的场景 |
| 状态迁移 | 对象有清晰状态机 | 状态由多个对象共同决定（组合爆炸） |
| 正交实验 | 多个独立配置项需要组合覆盖 | 配置项之间有依赖（正交表会给出无效组合） |
| 错误推测 | 有历史事故可参考 | 新品类、无经验可依（推测会退化成瞎猜） |

**方法不是并列选项，是分场景的工具。** 一个需求里通常同时用两三种：边界值测数量、状态迁移测姿态、场景法测流程。

## 用例写到多细

一条用例必须能让**别人不看需求文档就能执行**。三个要素缺一不可：

- **前置**：从哪个界面开始、角色处于什么状态、背包里有什么
- **操作**：具体的按键序列，不写"进行操作"
- **判据**：可观测的结果，不写"显示正常"

反例：

```
标题：测试背包拖拽
步骤：1. 打开背包  2. 拖拽物品
预期：功能正常
```

正例：

```
标题：背包满时从地面拖入物品应提示失败且不消耗地面物品
前置：背包 30/30 格已满；地面有 1 个"医疗包"
步骤：1. 靠近地面医疗包，打开背包
      2. 长按医疗包拖入背包第 1 格
      3. 关闭背包，重新打开
预期：步骤 2 弹出"背包已满"提示，物品回到地面原位；
      步骤 3 背包仍为 30/30，地面医疗包数量仍为 1
```

差别在第三行：**"关闭再打开"是一个判据动作**。少了它，就测不出"界面显示失败但数据已经写进去了"这类问题——而这类问题恰恰是最多的。

## 覆盖率怎么谈

覆盖率不是一个数，是四层，而且每一层都做不到 100%：

| 层 | 定义 | 现实能做到 |
|---|---|---|
| 功能点覆盖 | 需求列出的功能条目有几条测到 | 接近 100%，但需求本身会漏 |
| 路径覆盖 | 关键流程的每条主分支是否走到 | 主路径 100%，异常分支 60–80% |
| 状态迁移覆盖 | 合法迁移是否全走、非法迁移是否全拦 | 合法迁移可全覆盖，非法迁移只能抽重点 |
| 配置项覆盖 | 影响行为的配置组合是否覆盖 | 只能按正交或经验取子集 |

被问到"覆盖率多少"时，正确回答是**先说哪一层**：

> 功能点覆盖 100%，因为需求条目是可枚举的；状态迁移的非法迁移只覆盖了高频的十几条，物理上不可能的都跳过了；配置项用的是两因素组合，没有全组合。

**能说清哪一层没做到、为什么，比报一个 95% 可信得多。**

## 局限

这套顺序覆盖不了三类问题，遇到时要换方法或找人：

1. **并发与竞态**：两个玩家在同一帧对同一对象操作，单机测不出来，要构造多端同时操作或看服务端日志。
2. **数值平衡**：经济产出/消耗是否合理，是策划的数值模型问题，测试只能验证"规则按配置执行"，验证不了"配置本身对不对"。
3. **长时稳定性**：挂机几小时后的内存增长、状态累积，需要专项压测，不在功能用例范围内。

这三类如果没人负责，正确做法是**在测试报告里明确标为"未覆盖"并写明由谁补**，而不是含糊过去。含糊过去的代价是上线后由玩家发现。
