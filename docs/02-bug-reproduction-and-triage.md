# 偶现缺陷：从 1/3 复现率到根因

## 结论

偶现不是"复现不了"，是**条件还没收敛**。

三条信息必须记下来，缺任何一条，这个 bug 就交接不出去——别人接过去只能重新试，试几次失败就会挂起：

1. **环境**：机型、系统版本、画质档位、网络类型、当时的可用内存
2. **路径**：最短操作序列，从哪个界面开始，中间有没有跳过步骤
3. **时序**：操作和现象之间的时间关系，以及当时还有没有别的事在发生（后台下载、语音、断线重连、队友加入）

写清这三条，即使当下只有 1/3 的复现率，这个 bug 也进入了可维修状态。

## 为什么"偶现，无法复现"是最差的缺陷单

这句话不是信息，是**把问题退回给了发现者**。

它带来的后果是链式的：

- 开发看到后无法判断归属，会先问"是不是你网络问题"，一轮沟通过去一天
- 版本更新后现象消失，没人知道是真修好了还是条件变了
- 上线后集中爆发，此时再回头查，日志早过期了

反过来，"3 次复现 1 次，具体条件如下"的缺陷单，即使暂时定位不了，也能被排进计划——因为它可验证。

**复现率是信息，不是缺陷。** 1/3 意味着三次能验一次，修复后可以当场验证；"偶现"意味着修复后也没法验证，只能等它下次出现。

## 怎么把 1/3 提高

四个二分，按成本从低到高：

### 版本二分

换版本试。如果某个历史版本必现、当前版本不现，那你手上就有一个"曾经被改过的地方"的线索。这一步零成本，但很多人跳过。

### 设备二分

同一操作在高端机和低端机上各跑十次。差异往往直接指向问题类型：

| 现象 | 大概率是什么 |
|---|---|
| 只在低端机出现 | 帧率/时序相关，逻辑本身没错 |
| 只在特定 GPU / 系统版本出现 | 渲染层或平台差异，不是玩法逻辑 |
| 只在内存吃紧时出现 | 资源加载失败后的降级路径没处理 |

### 配置二分

画质、帧率上限、特效等级、语言、分辨率。把可疑项逐个关掉再试。

**如果关掉某一项后必现，那这项配置就是触发条件**，可以直接写进缺陷单，开发拿到就能定位。

### 数据二分

背包状态、任务进度、角色属性、仓库占用。很多偶现问题的真实触发条件是"某个数据处于特定状态"，而不是操作本身。

做法：复现前先截图记录当前数据状态，包括数量、品质、堆叠情况。等你发现两次复现时某个数值都相同，条件就找到了。

> 例子：某个道具在拾取时偶尔不进背包。最后发现触发条件是背包里已有同 ID 道具且堆叠数正好等于上限——拾取逻辑先判断"能否堆叠"，堆叠失败后没有落到"找空格位"的分支。这个条件从界面看不出来，必须先记录数据状态才能发现。

## 录屏和日志怎么对齐

有录屏没日志、有日志没录屏，都只能定位一半。两个都要，而且要能对上。

做法是**找锚点**：先确定现象发生的精确瞬间（比如道具数量从 3 变 0 的那一帧），再去日志里找同一秒的对应记录。

几个实操细节：

- **先对到秒，再对到帧**。日志通常只到毫秒，录屏按帧率走，硬对帧会错。
- **允许 1–2 秒偏差**。日志有缓冲，客户端写盘有延迟。差 2 秒以上的对齐不可信，不要在错误的基础上推结论。
- **锚点要选有唯一性的**。选"我点了一下按钮"对不上，选"道具数量从 3 变成 0"能对上。
- **注意本地时间**。有些日志打的是 UTC，差 8 小时，看起来像"日志里根本没有这个操作"。

对上了之后，判断链条就出来了：录屏里看到什么 → 那一刻客户端发了什么请求 → 服务端返回了什么 → 客户端拿返回值做了什么。

**这四段里断在哪一段，就是问题所在。**

## 定级：三个维度，别用"我觉得"

| 维度 | 问法 |
|---|---|
| 影响面 | 多少玩家、多少局能遇到？特定地图特定点位，还是每局都有？ |
| 阻断性 | 遇到了还能不能继续玩？卡死、掉线、进度丢失属于阻断 |
| 可绕过性 | 有没有替代路径？重启能恢复，还是永久损坏？ |

组合起来判断：

| | 可绕过 | 不可绕过 |
|---|---|---|
| **影响面大** | 严重 | 致命 |
| **影响面小** | 一般 | 严重 |

"影响面小且可绕过"给"一般"是有争议的——**如果它会导致玩家数据不一致，一律上调一级**。数据问题是不可逆的，玩家不会因为"重启能恢复"就原谅金币少了。

## 归属判定：四条可验证的动作

定级之后要判归属，否则缺陷会在客户端和服务端之间来回踢。每条都给一个能当场做的动作：

| 怀疑方 | 判别动作 | 结论怎么读 |
|---|---|---|
| 客户端表现层 | 换一台设备用同一账号复现 | 换设备不复现 → 客户端；仍复现 → 往下查 |
| 服务端逻辑 | 抓同一时刻的请求与响应 | 响应里数据就是错的 → 服务端；响应正确但界面错 → 客户端 |
| 配置表 | 直接查表核对这条数据 | 表里值本身不对 → 配置；表对但表现错 → 代码 |
| 需求理解错 | 回看需求文档原文 | 双方理解不一致 → 不是 bug，是需求要补一句 |

最后一条最容易被跳过。**很多"bug"的本质是需求没写清，判成 bug 会让开发改错方向。** 这种情况正确做法是提"需求待明确"，附上两种理解的差异，让策划选。

## 局限

这套方法对**单因素触发**的问题有效。三类情况它搞不定：

1. **时序交叉类**：网络抖动 + 帧率抖动 + 状态机切换同时发生。单机复现不了，需要构造环境（限速、限帧、注入延迟）或在服务端做全链路日志。
2. **概率极低类**：万分之一以下，靠手动试是统计不出来的。这类要靠自动化反复跑或加监控埋点，不能靠"再多试几次"。
3. **已经消失类**：版本更新后不再复现，但没找到原因。正确做法是保留缺陷单并标注"现象消失，根因未知"，而不是关闭——它大概率会在别的条件下回来。

遇到这三类，诚实的写法是"当前无法定位，已记录条件与日志，建议加监控"，而不是硬猜一个原因写上去。**猜错的原因比没有原因更贵**，因为它会让开发改错地方。
