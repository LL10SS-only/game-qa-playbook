# 回归范围怎么定：三次发版决策，和它们管不了的事

## 结论

冒烟 / 核心 / 全量不是三个覆盖率档位，是三次发版决策：

- 冒烟回答「**能不能发**」——产物是不是个能跑的东西
- 核心回答「**敢不敢发**」——主路径和改过的地方有没有坏
- 全量回答「**值不值得发**」——这批改动的风险，撑不撑得起跑一遍的成本

三级只说「覆盖多少」，判据就立不住，最后会退化成「这次时间紧，跑核心吧」，而「时间紧」不是一个判据。

还有一件事得先说清楚：**回归范围决定测不测，不决定改不改。** 最常出事的不是漏测，是测出来了、被判成「可以优化」，上线后玩家不认。这一条不在这套规则的管辖内，第六节单独说。

## 一、三级各回答一个问题

| 级别 | 回答的问题 | 覆盖对象 | 一条不过怎么办 |
|---|---|---|---|
| 冒烟 | 能不能发 | 主链路上的节点，一个节点一条 | 立刻退回，不做「记下来先发」 |
| 核心 | 敢不敢发 | P0 全量 + 本次改动波及的 P1 + 跨系统交叉 | P0 阻断；P1 可带单发，但要有人认领 |
| 全量 | 值不值得发 | P0 + P1 全量，P2 抽检 | 按缺陷分级走，不按级别一票否决 |

三级的差别不是「测得多少」，是「**谁有权拍板**」。冒烟不过，执行的人自己就能退回；核心不过，要测试负责人点头；全量发现的问题，得回到缺陷分级那套流程里判轻重。混在一起谈，就会变成「反正都是问题，都改」。

## 二、冒烟：只判通不通，不判好不好

冒烟的覆盖对象是**链路**，不是功能。一条链路上每个节点至少一条，节点内部只验「进去、出来、状态还在」：

```
启动 → 登录 → 大厅 → 匹配/组队 → 进局 → 局内一次完整交互 → 结算 → 回大厅
```

四个判据，缺一条冒烟就没有意义：

1. **只走正路。** 冒烟的职责是证明产物能跑，不是找 bug。在冒烟阶段设计异常分支，等于用最贵的人力做最便宜的检查。
2. **一条不过即退回。** 「先记下来继续跑」是冒烟最常见的失效方式——一旦允许带问题继续，冒烟就从门槛变成了形式。
3. **必须能在半天内跑完。** 要跑一天的冒烟不叫冒烟，叫核心。这个时长上限比覆盖范围更重要。
4. **不写优先级。** 冒烟里所有条目同级：过，或者不过。

## 三、核心：判据是「波及面」，不是「优先级」

核心级的常见错误是直接筛 P0 跑一遍。P0 只覆盖「本来就重要」的部分，覆盖不了「这次改动碰到的」部分——而后者才是新风险的来源。

核心级的范围是三块的并集：

| 来源 | 为什么在核心级 |
|---|---|
| P0 全量 | 这些坏了就是事故，任何版本都不能省 |
| 本次改动波及的 P1 | 改动附近的用例，风险随改动走，不随优先级走 |
| 跨系统交叉 | 单独看都对、凑一起才坏的组合，最容易在版本间被漏掉 |

**「波及面」怎么定**：从这次的提交记录往回推，不是从需求文档往回推。需求写的是「改了什么功能」，提交记录写的是「动了哪些模块」，后者才是真实影响范围。一个只改了配置表数值的提交，需求上可能只是「调整手感」，波及面却是所有引用这张表的系统。

退出条件要写死，否则「核心跑完了」会变成一句主观判断：

- P0 全过，无例外
- P1 允许带单发，但每条必须写明责任人和目标修复版本
- 跨系统交叉项全过

## 四、全量：算一笔账，再决定做不做

全量级真正的约束是**人力**，不是风险偏好。用 854 条用例、每条 5 分钟估：单人约 71 小时，也就是九个工作日。没有一个正常版本周期容得下这个数。

所以「全量」在实践中只有三种形态，选哪种要看改动性质：

| 形态 | 适用 | 做法 |
|---|---|---|
| 全真跑 | 改底层、改数值公式、跨版本累积多次小改 | 拆给多人并行，按模块切，交叉项单独一组 |
| 全量抽样 | 改动可穷举，但覆盖面广 | P0 + P1 全跑，P2 按模块轮换抽，每版抽不同的模块 |
| 免全量 | 三个条件同时成立 | 见下 |

**可以免全量的三个条件，必须同时满足：**

1. 改动是**加法的**，不是改法的。新增一个道具是加法，改伤害公式是改法。
2. 改动范围**可穷举**。能列出这次受影响的全部系统，列不出就是不可穷举。
3. 上一个全量轮次距现在不超过两个版本。中间没有攒下未验证的债。

三条只满足两条，就退回抽样。这条比「时间紧就少跑点」可靠，因为它是可以当场举反例的：面试官问「只加了个道具，为什么还要跑全量」，答案是「因为它改了道具表的字段结构，所有读这张表的系统都受影响」——这就说明第 2 条不成立。

## 五、「先砍优先级低的」这句话不够用

按优先级从低往高砍，方向没错，但会砍错东西。优先级标签是**缺陷影响**的评级，不是**用例风险**的评级，两者不总是一致。

砍之前，每个候选问三个问题，按顺序：

| 判据 | 砍得掉 | 砍不掉 |
|---|---|---|
| 失败后玩家能不能自己绕过 | 能绕过（换条路、重开一局） | 不能绕过（卡死、丢档、必须重启） |
| 失败后有没有数据或资产损失 | 无损失，只是观感不对 | 有损失（道具、进度、货币） |
| 是不是已经在别处被覆盖 | 别的地方测过同一件事 | 只有这一条路径能测到 |

三问都是「砍得掉」才砍。任意一问落在「砍不掉」就留下，**不管它标的是 P1 还是 P2**。

典型的分歧就出在这里：道具复制的边缘路径，标 P2，但它满足「不能绕过 + 有资产损失」，所以不能砍；而多端组合下的界面适配，标 P1，但它能绕过、无损失、且在单端用例里已经覆盖，就可以砍。

三问的作用不是替代优先级，是给「先砍低优先级」加一道刹车。

## 六、规则管不到的那一类：测出来了，判成不用改

到现在为止，没有因为砍全量出过上线事故。但有一类问题一直在发生，而且不在上面任何一条规则的射程内。

现象是：测试期发现了，提单了，评估结论是「不影响功能，可以后续优化」；上线后玩家反映强烈，紧急改。

**它不是漏测。它测到了，也报了，卡在了「判」这一步。**

这类问题的共同特征很一致：

- 不阻塞、不掉线、不崩溃——任何按「能不能用」设计的判据都会放它过去
- 不在标准操作路径上——它出现在「玩家实际会做但用例没当回事」的动作里
- 单看每一项都「轻微」——只有连续做了二十次、或者连着看了两个小时，总量才变得难以忍受

所以它天然游离在三级体系之外：冒烟管不到（不阻塞），核心管不到（不在波及面里，因为没改那部分），全量也管不到（全量跑的仍是同一批判据）。

**在这套规则上加一条是不够的，得加一条通道。** 两个动作：

1. **在缺陷分级里给「体验类」一个独立档位**，不和功能缺陷比轻重。它的判据不是「能不能用」，是「有没有人会为它专门发一条反馈」。这一档不设「暂不修复」这个选项，只设「本版改」和「记录进体验清单」。
2. **上线后 72 小时的反馈回收要有明确去处。** 没有去处，同一批问题会在下一个版本被重新发现、重新评估、再次判成「可优化」——循环三次之后，团队会学会不再提它。

最后一句是这套东西里最贵的一条经验：**玩家不会按你的分级标准提意见。**

## 局限

- **依赖发版节奏。** 三级的前提是有相对固定的版本周期。日更或无版本概念的项目用不上，得换成按提交批次切。
- **判据需要历史数据。** 「波及面」要靠提交记录和此前的缺陷分布推，新项目前两个版本没有这个数据，只能保守做全量。
- **管不了需求变更。** 需求中途改了，前面的波及面分析全部作废，这时候唯一可靠的做法是重新推一遍，而不是在旧范围上加减。
- **对首次测试和大版本无效。** 这两种情况没有「上一轮」可比，全量是唯一选项。
- **第六节那类问题只解决了一半。** 独立档位能保证它不被判「暂不修复」，但「玩家会不会真的难受」仍然要靠人判断，规则替代不了这个判断。
